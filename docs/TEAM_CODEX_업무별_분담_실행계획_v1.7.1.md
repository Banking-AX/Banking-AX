# Banking AX — 2인 Codex 업무별 분담·병렬 개발 실행계획

> 기준: 2026-10-23 / 기능명세서 v1.7.1 / **팀 합의용 구현 운영 문서**  
> 적용 대상: Spring Boot + JPA + MySQL, FastAPI + LangGraph, React 기반 금융업무 PoC  
> 목적: **같은 파일을 고치는 일을 최소화**하면서, **두 사람 모두 고객·직원 Agent와 Spring Tool·RAG·테스트를 직접 구현**한다.

## 0. 한 문장 결론

**금융업무는 코드별로 완전히 수직 분담하고, 공통 코드에는 단일 소유자를 둔다.** 각자 A·B·C 업무 하나씩을 고객 화면 → Spring → Agent → 테스트까지 끝까지 구현한다. 공통 계약은 작게 유지하고, 상세 요청·응답 스키마는 각 업무 폴더에서 소유한다.

이 방식은 충돌 가능성을 **줄이는 것**이지 기술적으로 0으로 만드는 것은 아니다. `AGENTS.md`는 Codex에 대한 지침이며 파일 접근 강제 장치는 아니다. PR의 실제 변경 파일과 계약 테스트로 검증한다.

### 변경할 수 없는 제품 정책(v1.7.1)

1. A는 Spring 조회, B는 Spring Java 규칙과 명시적 고객 동의에 따른 Mock 변경, C는 직원의 **모의 접수 검토 결과**가 책임을 진다. AI는 금융업무 결과·법적 적격성을 최종 확정하지 않는다.
2. C 흐름: **고객 제출 → 직원 Agent 사전점검 → 직원 검토 결과 확정·웹 통지 → `진행 가능` 건에 한해 고객 방문 예약 → AI 직원 추천 → Spring 확정**. C 제출 시 예약을 먼저 생성하지 않는다.
3. C-02는 검토 결과 후 방문 예약을 지원한다. C-01도 비대면이 기본이지만 **직원이 방문 필요로 안내한 건은 결과 후 예약할 수 있다**. A/B에는 예약 없음.
4. OCR/문서 파서는 **출처·양식이 검수된 신한은행 공식 양식에만** 적용한다. 일반 가족관계·기본·소득·과세증명서의 내용 OCR은 범위 밖이다.
5. 직원 추천은 **지원 업무 코드와 현재 업무량**을 기반으로 한다. 가상의 경력·전문성 점수를 만들어 쓰지 않는다. Spring만 예약·직원 배정을 확정한다.
6. 채팅 본문 7일, Case용 최소 업무 진술 요약 30일; 제출 전 72시간 무활동은 **임시 입력 초기화**다. 제출 Case나 감사 이력은 초기화하지 않는다.
7. 직원 점검 전 고객 취소 가능(경합은 Spring이 원자적으로 확인), 예약 변경/취소는 **방문 24시간 전까지**. B/C 결과 이메일, A 이메일 미발송.
8. '채무조정 접수'라는 제품 용어가 **법적 효력이 있는 정식 은행 접수·통지 시스템 완성**을 뜻하지 않는다. 실제 은행 시스템과 연동하지 않는다.
9. **B-01/B-02 실행 직전, C-01/C-02 최초 제출 직전**에는 필수 동의 → 프론트 모의 서명 → SOLAPI SMS 인증(Spring 전담) → Spring 재검증을 거친다. 서명 획·이미지는 저장하지 않고, 인증번호는 Spring 메모리 캐시 TTL로만 보관한다 `[제안]`. A 조회·추가 확인·직원 결과·예약에는 SMS를 요구하지 않는다.

## 3. Phase 0 — 무거운 공통 기능 완성이 아니라 **계약 + 작동하는 최소 연결**

Phase 0에서 모든 Case·서류·예약을 완성하려고 하면 병렬 개발을 시작할 수 없다. 다음 9개의 계약을 확정하고 **Stub/Fake 소비자 테스트**를 만든 뒤 각자 업무를 착수한다.

| 공통 계약 | 소유자 | Phase 0에서 고정할 최소 내용 | 실제 구현이 늦을 때 |
|---|---|---|---|
| `TaskHandler` (Spring) | 팀원 1 | `taskCode`, `start`, `resume`, `hold`, `complete`의 입력·출력/상태 책임 | 인터페이스 + 테스트용 InMemory 구현 |
| `register_task` (FastAPI) | 팀원 1 | 코드별 모듈 등록 방식, 이름/입력/출력, 허용 Tool 목록 | 등록만 되는 고정 응답 그래프 |
| Tool Gateway / 공통 오류 | 팀원 1 | 인증·actor/role, `taskCode`, `workItemId`, `requestId`, errorCode, traceId | JSON 계약과 Stub HTTP 엔드포인트 |
| CasePort | 팀원 1 | Case 생성·제출/취소·revision·직원 검토 시작/결과·고객 확인 응답 | Fake CaseStore + 실제 DB 인터페이스. **모든 ServiceCase 기능 완료는 Phase 0 요건 아님** |
| DocumentPort | 팀원 2 | `requiredDocumentId`, `documentFileId`, `version`, mime/크기/상태 | 실제 파일 저장 전에 Fake DocumentStore |
| `register_check` | 팀원 2 | `caseId + revision + taskCode + input` → 소스·결과·근거 포함 구조화 `reviewItems` | 고정 JSON 검토 노드, 테스트 가능한 함수 |
| NotificationPort | 팀원 2 | B/C 이메일·Case 결과 웹알림, 이벤트 ID, 멱등 | 로그 Stub (실발송 전) |
| VerificationPort | 팀원 1 | `issue(workItemId, action)` → 마스킹 번호·만료 시각, `verify(code)` → 바인딩 근거, `consume(binding, requestVersion)` 1회 소비 | 모의 송신기(테스트 프로필 전용) + 메모리 저장 |
| VisitPort | 팀원 2 | **직원 결과 `진행 가능` 및 웹 통지 후에만** `SELECTED → PENDING_ASSIGNMENT → CONFIRMED` 등 | 검토 완료 Fixture + 가짜 지점/슬롯 응답 |

**동시에 고정:** 6개 업무 코드, Workflow/WorkItem/Case/review/예약 상태 명칭, Spring→FastAPI 인증 범위, DB DDL 기준, 직렬화 가능한 API 요청·응답 예시.

**계약 파일 배치(예시):**

```text
docs/contracts/
  core/                         # owner: 팀원 1, 공통 외피·상태코드·에러
  auth-verification/            # owner: 팀원 1, SIGN/SMS 요청·응답·오류 코드
  a01/ a02/ b01/ b02/ c01/ c02/ # 각 업무 주인 소유, Tool API·스키마·테스트 예시
  staff-review/                 # owner: 팀원 2, 결과 타입·근거 메타
  visit/                        # owner: 팀원 2, 예약·배정 요청·응답
```

- **공통 계약에는 업무별 모든 필드를 나열하지 않는다.** 공통에는 ID/버전/요청ID·오류·보안/상태만. 업무 상세 파라미터/규칙은 업무별 계약에 둔다.
- 계약 변경은 ‘코드 변경 전’ PR로 제안하고 상대 승인 후 병합한다. `core-v1` 태그는 **호환성 기준점**이지 구현 파일/내부 함수를 영원히 수정하지 말라는 의미가 아니다. 호환 변경은 테스트로 확인한다.
- Spring `TaskHandler`는 Bean 자동 발견 가능. Python `register_task/register_check`는 **선언된 등록 목록을 로딩하는 방식**으로 설계한다. 부작용이 있는 모듈의 무차별 자동 import는 금지한다.
- 공통 응답 예시(필드는 실제 DTO 합의 후 변경 가능):

```json
{
  "requestId": "req-001",
  "taskCode": "INHERITANCE_DEPOSIT",
  "workItemId": 100,
  "caseId": 200,
  "revision": 1,
  "data": {},
  "error": null
}
```

**Phase 0 완료:** 합성 사용자 A-02 조회 하나가 `고객 요청 → FastAPI 고객 Graph → Spring Tool → 응답`을 왕복하고, C-01/C-02의 접수/점검 요청 DTO를 각각 Fake로 호출하는 계약 테스트가 통과한다. **직원 Agent/OCR/예약 전체 완성은 Phase 0 요구사항이 아니다.**

## 4. 실행 단계 — 작업이 막혀도 병렬 진행 가능하도록

| Gate | 팀원 1 | 팀원 2 | 통과 조건 |
|---|---|---|---|
| **G0 계약·환경** | MySQL 스키마 적용·Spring 인증 기본, TaskHandler/CasePort/Tool 계약, A-02 최소 왕복 | FastAPI 실행·`register_check`/DocumentPort/VisitPort Fake, React 화면 셸 일부 | 공통 계약 테스트, 두 Agent 프로세스 연동, 다른 팀원 계약 소비 가능 |

## 5. 충돌 방지: Codex가 수정 가능한 경로를 작업마다 지정

```text
repo/
  AGENTS.md                        # 소유: 팀원 1 / 협업 규칙 참조
  docs/
    00_기능명세서_v1.7.1.md         # 기능·정책 정본
    04_UI_화면목록.md               # 시안 기준 화면·상태·문구 (참고)
    01_schema_mysql8.sql          # 실제 DB 기준
    contracts/{core,auth-verification,staff-review,visit,a01,a02,b01,b02,c01,c02}/
    TEAM_CODEX_업무별_분담_실행계획_v1.7.1.md
  backend/
    core/{auth,verification,workflow,case,tool} # 팀원 1
    core/{document,notification,visit} # 팀원 2 (실제 Java 패키지 경계 확정)
    task/{a02,b01,c01}/           # 팀원 1
    task/{a01,b02,c02}/           # 팀원 2
  ai-server/app/
    core/{customer_router,task_registry,tool_gateway}/  # 팀원 1
    core/{staff_engine,check_registry,document,rag}/     # 팀원 2
    tasks/{a02,b01,c01}/          # 팀원 1
    tasks/{a01,b02,c02}/          # 팀원 2
    assignment/                   # 팀원 2
  frontend/src/
    shared/{auth,chat,shell,esign}/ # 팀원 1
    shared/{upload,notification,report,visit}/ # 팀원 2
    features/{a02,b01,c01}/       # 팀원 1
    features/{a01,b02,c02}/       # 팀원 2
```

위 경로는 **예시**다. 실제 Git 리포지토리 구조를 먼저 조회하고 중복 패키지를 만들지 않는다. *폴더 단위보다 파일 단위 소유권*을 우선한다. 중앙 `pom.xml`, `application.yml`, `package.json`, FastAPI 진입점, 프론트 Router, DDL, GitHub Actions 같은 공유 파일은 정본 파일별 담당자 1명만 수정한다.

**Git 정책**
1. `main` 보호, 업무별 브랜치 `feat/t1-c01-review`, `feat/t2-c02-intake`, 공통은 `core/t1-*`, `core/t2-*`.
2. **한 PR은 하나의 계약 또는 테스트 가능한 기능**. `git diff --name-only`로 타인 영역 변경 검사; 범위 넘는 코드는 원복하고 별도 요청.
3. 공통 계약/DB 변경 PR → 리뷰·승인·병합 → 다른 작업 브랜치가 최신 main으로 갱신 → 구현 PR.
4. `git fetch origin && git rebase origin/main` 등으로 자기 작업 브랜치를 최신화한 뒤 충돌 재검증. 이미 팀원이 소비하는 공유 브랜치에서는 강제 push 금지.
5. **Flyway 버전을 팀원 1=100번대, 팀원 2=200번대로 나누지 않는다.** 번호가 큰 마이그레이션이 먼저 배포되면 나중에 합쳐진 낮은 번호가 적용되지 않을 수 있기 때문이다. 팀원 1이 매 PR의 병합 순서에 맞춰 버전 순서와 스키마 호환성을 검증·커밋한다. 이미 적용된 버전은 수정하지 않고 신규 버전 추가.
6. Mock 시드는 `seed/core_customers.sql` 공통 1개(소유자 지정) + 업무별 별도 파일. 테스트 계정/ID 중복 회피.
7. `CODEOWNERS`는 리뷰 요청을 도울 뿐 실제 동시 수정·충돌을 금지하지 못한다. PR 변경 목록과 CI가 최종 방어선이다.

**공통 파일 변경 절차:** `(1) 목적·기능 ID·계약 차이·테스트 영향 작성 → (2) 담당자 승인 → (3) 해당 공통 파일의 1개 PR에서 수정 → (4) 업무 브랜치 최신화 → (5) 계약/E2E 재검증`. 긴급 버그 수정을 배운 경험으로 남기려면 해당 PR 동안 파일 소유권을 **명시적으로 넘겨받는다.**

### 이 문서의 성격

팀원과 Codex가 동일한 방식으로 작업하기 위한 **분담·협업 실행계획**이다. 실제 리포지토리의 폴더·클래스·API를 아직 검사하지 않았으므로 예시 경로·인터페이스 명은 **설계안**이며, 첫 합의 커밋에서 정확한 경로로 교체한다. 기능 정책과 DB 구조의 최상위 기준은 항상 v1.7 기능명세서와 MySQL 실행용 DDL이다.
