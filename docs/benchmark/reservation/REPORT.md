# 영업점 예약 현실 부하·동시성 검증 (2026-11-09)

기존 동시 요청 20~100건 실험은 폐기하지 않고 **극한 경합 테스트**로 재분류한다. 이 문서는 업무 흐름을 반영한 별도 측정이다. 원본은 `results/`, 재현은 `scripts/run_profile.sh`.

## 환경

- 대상: 현재 작업 트리로 빌드한 JAR (`26d4f68` + 미커밋 변경). Flyway V14까지 적용한 임시 MySQL 8.0.36.
- 경로: 로그인 JWT를 쓰는 실제 고객 API (`/api/v1/customer/reservations`). 기존 서버와 공유 DB 미사용.
- P0: 컨테이너 제한 없음 (16 vCPU). P1: Spring과 MySQL이 CPU 1개를 공유, 각 3GB.
- 부하기: 같은 PC의 Python. CPU는 Spring, MySQL, 부하기를 분리 집계했으나 물리적으로 분리되지는 않았다.
- 프로필별 102회 측정, 총 204회. 회차마다 예약·이력·알림을 비우고 시작. 워밍업 120요청은 제외.
- 잠금 대기: MySQL `performance_schema`의 `select id from branch where id=? for update` 실행 시간. 트랜잭션: 같은 스레드의 `events_transactions` 시간.

## 코드 기준 업무 규칙

| 항목 | 구현 |
|---|---|
| 예약 가능 Case | 본인 소유, `REVIEW_PASSED`, `result_notified_at` 있음 |
| 직원 자격 | 해당 지점의 활성 `STAFF`, 그 시각 미배정. `staff_task_capability` 테이블이 없어 업무코드 필터 없음 |
| 배정 | 현재 업무량이 적은 순, 동률이면 직원 ID 순 (기본 mock 어댑터) |
| 시간대 | 평일 10, 11, 13, 14, 15시. 내일 이후 7일 이내, 24시간 이후만 예약 |
| API | 가능 시간 조회, 생성, 목록, 변경, 취소 |
| 잠금 | 생성·변경 트랜잭션의 첫 조회에서 `branch` 행 `FOR UPDATE`, 커밋까지 유지 |
| 최종 방어 | `active_case_id`, `active_staff_slot` UNIQUE |

**임의 가정 (은행 통계가 아님):** 지점 직원 2/3/5명, 세션 도착 초당 1건·3건(포아송), 생각 시간 0.3~1초, 변경 비율 25%, 인기 시간대는 2초 안에 5~10명 도착.

## 시나리오

- **A 일반 업무:** 가능 시간 조회, 생성, 목록, 일부 변경. 3개 지점, 3회 반복.
- **B 인기 시간대:** 직원 2명 시간대에 고객 5, 8, 10명이 2초 안에 도착. 5회 반복.
- **L 잠금 범위:** 동시 10, 20건, 3개 배치, 10회 반복.
- **C 장애·극한:** 동일 요청번호 재전송, 동시 변경, 동시 20~100건. 3회 반복.

## 측정하지 못한 것

- HikariCP 커넥션 대기 (애플리케이션 지표 없음). 기본 풀 10이라 동시 20건은 풀 대기가 포함된다. HTTP와 트랜잭션의 차이를 풀 대기로 단정하지 않는다.
- 실제 1 Core / 8GB VM 측정. P1은 로컬 Docker의 근사치이고, FastAPI·RAG 임베딩·프론트 부하와 메모리가 빠져 있다.
- 지점+시간 단위 잠금의 실제 성능 (코드 수정 없이 비교 불가).
- 원격 네트워크 지연, 장시간 안정성, 실제 은행 도착 패턴.
- HTTP 순위 어댑터 사용 시 영향. 순위 계산은 잠금 안에서 실행되므로 외부 호출로 바꾸면 잠금 시간이 늘어난다.

## 판단

- **시연용 서비스에는 현재 설계가 적절하다.** 일반 부하의 잠금 비용은 무시할 수준이고 정합성 실패가 없었다.
- **지금 잠금 범위를 바꿀 필요는 없다.** 같은 지점 다른 시간대의 불필요한 대기는 실측으로 확인했지만, 동시 10건 이상이 같은 지점에 몰릴 때만 드러난다. 운영 트래픽을 측정해 같은 지점 동시 요청이 일상적이면 지점+시간 단위 잠금을 검토한다. `branch_slot` 테이블이 Flyway에 없어 스키마 결정이 먼저 필요하다.
- 기존 100명 확정률(25~34% → 100%)은 **극한 조건의 버그 수정 근거**이며 은행 평균 성능이 아니다.
