# Banking-AX 서비스 수준 실측 검증

## 1. 예약 동시성: 실제 HTTP + 격리 Spring/MySQL

### 환경

- Docker 전용 네트워크 `bankingax-bench-net`, 신규 MySQL 8.4 스키마 `banking_ax_bench`.
- Spring Boot JAR은 별도 컨테이너에서 포트 `18091`으로만 노출했고, Flyway V1–V14 적용 로그를 확인했다. 기존 18081/9001/5175 및 공유 DB에는 연결하지 않았다.
- Fixture: 직원 2명, 서로 다른 고객 20명·`REVIEW_PASSED` C-02 Case 20건, 동일 지점·동일 유효 슬롯(2026-11-10 10:00 KST).
- 요청: 내부 고객 API `POST /api/v1/reservations`, 각 고객 ID/Case ID/requestId를 다르게 하여 Python 20 스레드 barrier로 동시 시작. Fixture를 매 회 재적재해 3회 반복했다.

### 실제 측정값

| 반복 | HTTP 요청 | 확정(2xx) | 업무상 거절 | HTTP 5xx | HTTP p50 / p95 | 처리량 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 20 | 2 | 18 | 0 | 558.322 / 569.579 ms | 34.967 req/s |
| 2 | 20 | 2 | 18 | 0 | 338.092 / 347.024 ms | 57.549 req/s |
| 3 | 20 | 2 | 18 | 0 | 248.463 / 256.520 ms | 62.175 req/s |

각 회의 격리 MySQL 사후 조회 결과는 동일했다.

| DB 검증 | 반복 1 | 반복 2 | 반복 3 |
|---|---:|---:|---:|
| `CONFIRMED` 예약 | 2 | 2 | 2 |
| 동일 직원·동일 시간 활성 중복 | 0 | 0 | 0 |
| 동일 Case 활성 예약 중복 | 0 | 0 | 0 |

### 중요한 API 계약 관찰

18개 업무상 거절은 응답 본문의 `RESERVATION_CONFLICT` 또는 `RESERVATION_SLOT_UNAVAILABLE`이었다. 그러나 현재 Spring 예외 매핑은 이를 **HTTP 400**으로 반환했다. 따라서 이번 실측에서 HTTP 409은 0건이며, 이는 “충돌이 없었다”가 아니라 **업무 충돌을 409로 매핑하지 않는 구현 상태**를 뜻한다. 5xx는 3회 총 60건에서 0건이었다.

### 재현

```powershell
# MySQL/격리 Spring을 기동한 상태에서, 매 반복 전 Fixture 재적재
Get-Content scripts/benchmark/fixtures/reservation_20_concurrent.sql |
  docker exec -i bankingax-bench-mysql mysql -ubench -pbench_pw banking_ax_bench
$env:BENCH_BASE_URL='http://127.0.0.1:18091'
$env:BENCH_GATEWAY_TOKEN='bench-token'
$env:BENCH_SLOT_START='2026-11-10T10:00:00+09:00'
ai-server/.venv/Scripts/python.exe scripts/benchmark/run_reservation_http.py
```

원본 요청별 결과는 `docs/benchmark/results/reservation_http_latest.json`에 마지막 반복 기준으로 저장된다.

## 2. C-02 실제 연결 성능

이번 실행에서 **미측정**이다. Spring/MySQL은 기동했지만, 실제 C-02 submit → Spring `StaffAgentHttpClient` → FastAPI `/staff-agent/check` → Spring review persistence까지의 완전한 연결을 검증할 별도 FastAPI 컨테이너, C-02 제출 인증 Fixture, 그리고 실행 JAR과 현재 소스의 동등성 검증이 이번 격리 환경에 아직 준비되지 않았다.

따라서 오프라인 `c02_precheck_benchmark.py` 수치를 HTTP API 성능으로 인용하지 않는다. OCR은 이번 실제 HTTP 예약 측정에서 호출되지 않았고, 기존 C-02 오프라인 fixture의 OCR 상태는 Mock 메타데이터다.

## 3. 기존 오프라인 지표 재검토

기존 30건은 5종 시나리오 × 6건이다. 정상 6건은 기대 신호 0개이고, 나머지 4종 × 6건은 각 1개여서 **기대 신호 분모는 24개**다. `deterministicRuleItems=18`은 누락 6 + `VALIDATION_FAILED` 6 + `NEEDS_SUPPLEMENT` 6의 `SPRING_RULE` 항목만 센 값이다. `staffReviewItems=54`는 모든 Case에 공통 `DOCUMENT_POLICY` 30개, 위 18개, `UNCONFIRMED_ABSENT` 6개를 합산한 값이다.

이 fixture의 기대값은 구현과 독립적인 임상 정답지가 아니다. 특히 OCR 불일치/판독 불가의 기대 범주는 구현이 받는 상태(`VALIDATION_FAILED`/`NEEDS_SUPPLEMENT`)를 `DOCUMENT_NEEDS_SUPPLEMENT`에 대응시킨 것이므로, 24/24 및 0/0은 **규칙 분기 회귀검증**일 뿐 정확도 추정치로 사용하면 과대평가된다. Fake LLM p50/p95도 실제 AI 응답시간으로 사용하면 안 된다.

## 4. 다음 실제 C-02 측정의 준비 조건

1. 버전 고정된 Spring JAR을 소스 SHA와 함께 build하고 별도 컨테이너에 탑재.
2. FastAPI도 별도 컨테이너로 기동하고 `STAFF_AGENT_GATEWAY_TOKEN`, `APP_STAFF_AGENT_BASE_URL`을 격리 네트워크 내부 주소로 설정.
3. 인증·서명·Mock SMS를 통과하는 C-02 submit Fixture와 정상/누락/OCR Mock 불일치/판독불가/직원확인 Case를 독립 기대표로 준비.
4. HTTP 응답, `agent_review_run`, `review_item`, `service_case.review_status`를 함께 대조하고 규칙/RAG 결과와 opt-in 실제 LLM 결과를 별도 실험으로 기록.
