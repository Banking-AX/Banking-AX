# T2–T1 통합 계약 및 브라우저 검증 절차

이 문서는 T2 업무 화면과 T1 소유 Chat·인증·공통 셸의 연결 지점을 고정한다. T1 소유 파일은 T2에서 수정하지 않는다.

## 최신 T1 셸 상태 (2026-11-03)

통합 전 확인한 `origin/main`은 `d913a018`이며, T1의 업무 기록 UI는 `/work` → `WorkRecordsPage` → `WorkRecordsView`로 등록되어 Mock adapter를 사용한다. 이 상태에서 T2의 실제 DB 이력 API는 별도 `/api/v1/customer/task-history` 계약이다. 두 이력 화면의 중복을 피하려면 T1이 기존 `/work` 화면의 adapter를 T2 API로 교체하거나 라우트 연결을 조정해야 한다. T2 브랜치는 최신 main을 merge/rebase하지 않았다.

## 업무 시작 및 화면 진입 계약

| 업무 | `taskCode` | 진입 경로 | WorkItem 발급 |
|---|---|---|---|
| A-01 거래내역 조회 | `TRANSACTION_SEARCH` | `/tasks/a01/{workItemId}` | 서버 Workflow가 생성한 ID만 전달 |
| B-02 청약통장 모의 해지 | `HOUSING_SAVINGS_CLOSE` | `/tasks/b02/{workItemId}` | 서버 Workflow가 생성한 ID만 전달 |
| C-02 상속예금 사전접수 | `INHERITANCE_DEPOSIT` | `/tasks/c02/{workItemId}` 또는 기존 Case 재진입 경로 | 서버 Workflow가 생성한 ID만 전달 |

Chat/WorkflowStart가 WorkItem을 만들고, 결과에는 `taskCode`, `workItemId`, `workItemStatus`를 포함해야 한다. Workflow aggregate의 `workflowStatus`와 개별 WorkItem의 `workItemStatus`는 별도 필드다. 업무 화면으로 이동할 때 `frontend/src/tasks/taskNavigation.ts`의 `taskPathForWorkflow`를 사용한다. 브라우저에서 ID를 만들거나 추측하지 않는다. 화면은 `ACTIVE`인 올바른 task만 진행 경로로 연다.

## 고객 업무 이력과 재진입

- `GET /api/v1/customer/task-history`는 JWT 인증 고객의 WorkItem만 반환한다. 고객 ID는 토큰 principal에서 정한다.
- 응답 항목: `taskCode`, `workItemId`, `workItemStatus`, `workflowStatus`, `caseId`, `caseStatus`, `resultAvailable`.
- 화면 구현: `frontend/src/pages/CustomerTaskHistoryPage.tsx`; 링크 정책은 `frontend/src/tasks/taskHistoryNavigation.ts`.
- DONE A-01 결과: `GET /api/v1/customer/a01/work-items/{workItemId}/result`, 화면 경로 `/tasks/a01/{workItemId}?view=result`.
- DONE B-02 결과: `GET /api/v1/customer/b02/work-items/{workItemId}/result`, 화면 경로 `/tasks/b02/{workItemId}?view=result`.
- C-02는 이력 API가 돌려준 본인 `caseId`로 `/tasks/c02/cases/{caseId}`에 재진입한다. 고객 화면 데이터는 C-02 snapshot API에서 다시 읽는다.

**T1 셸 연동 요청:** 최신 main에는 이미 CUSTOMER guard가 있는 `/work` 및 T1의 `WorkRecordsPage`/Mock adapter가 있다. T2는 이를 덮어쓰지 않았다. T1과 합칠 때 선택지는 (1) `/work`의 `WorkRecordsPage`가 T2 `GET /api/v1/customer/task-history`를 읽도록 T1 소유 화면을 통합하거나 (2) T2 API 페이지를 `/tasks/history`에 별도 등록하고 기존 업무 요청 기록 내비게이션을 그 경로로 연결하는 것이다. 중복 메뉴/이력 화면이 생기지 않도록 T1이 경로를 결정해야 한다. `frontend/src/App.tsx` 및 메인 내비게이션은 T1 소유라 T2에서 변경하지 않았다.

## C-02 고객·직원 흐름

고객 BFF는 `POST /api/v1/customer/c02/prepare`, `POST /api/v1/customer/c02/{caseId}/documents/upload`(multipart), `GET /api/v1/customer/c02/{caseId}/snapshot` 및 문서/OCR 조회 계약을 사용한다. 업로드 응답의 최신 revision을 다음 요청에 사용한다. OCR은 Mock/설정된 adapter 결과를 참고자료로 보이며 사람의 원본 검토를 대체하지 않는다.

직원 경로는 STAFF 로그인 후 `GET /api/v1/staff/c02/{caseId}/staff-case`, `POST /api/v1/staff/c02/{caseId}/staff-precheck`, `POST /api/v1/staff/c02/{caseId}/staff-decision` 순서다. Agent 사전검토는 최종결정이 아니며, 결정은 직원 API 호출로만 기록된다. 고객은 `GET /api/v1/customer/notifications`에서 본인 알림을 확인한다.

방문 예약은 직원의 `PROCEED` 결정과 결과 웹 통지가 기록된 이후 고객이 요청한다. 현재 UI/API의 `PENDING_ASSIGNMENT`는 예약 요청 접수이며 직원 배정 또는 예약 확정이 아니다. T2는 직원 자동 배정을 여기서 약속하지 않는다.

## 라우트 등록 및 역할 경계

T1은 실제 API 이력 화면/라우트를 CUSTOMER guard로 감싸고 기존 JWT 갱신·인증 구조를 그대로 사용한다. 직원 C-02 화면은 기존 STAFF/EMPLOYEE 보호 라우트 아래 둔다. 고객 요청 본문의 임의 `customerId`, actor ID, 내부 Tool Gateway token을 신뢰하거나 브라우저에 추가하지 않는다.

## 통합 브라우저 절차

1. Spring과 React를 기존 환경 설정으로 기동하고, 테스트용 MySQL/Flyway 상태를 확인한다. 실제 CLOVA, SMS, 금융 API를 사용하지 않는다.
2. CUSTOMER로 로그인한 뒤 Chat에 A-01, B-02, C-02 요청을 각각 입력한다.
3. Chat/Workflow 응답의 서버 발급 `taskCode`, `workItemId`, `workItemStatus`를 확인하고 `taskPathForWorkflow` 경로로 업무 화면에 진입한다. Workflow 상태와 WorkItem 상태를 혼동하지 않는다.
4. A-01을 실행하고 완료 화면 및 업무 이력의 저장 결과 재진입을 확인한다.
5. B-02에서 규칙 결과, 필수 동의·모의 서명 UI·테스트 환경 OTP·실행 결과를 확인한다. 모의 서명은 법적 전자서명이 아니며 테스트 OTP를 운영에서 사용하지 않는다.
6. C-02 Case를 준비하고 허용 문서를 업로드한다. 고객 화면에서 Case ID, revision, OCR 방식/상태 및 수동 확인 필요 표시를 확인한다.
7. 별도 STAFF 세션에서 Case를 조회하고 최신 revision의 사전검토를 실행한 뒤 실제 직원 결정 API를 호출한다.
8. CUSTOMER 세션에서 본인 알림을 다시 읽고, 진행 가능 통지 후에만 예약을 요청한다. `PENDING_ASSIGNMENT`가 확정으로 표시되지 않는지 확인한다.
9. 새로고침 후 업무 이력에서 A-01/B-02 결과 또는 C-02 Case로 재진입되는지 확인한다.

## 확인된 제한

- Chat이 세 업무의 Workflow/WorkItem을 실제 생성하고 위 계약을 반환하는지는 T1 Chat 통합 테스트에서 확인해야 한다. 화면은 해당 ID를 발급하지 않는다.
- 이력 페이지 컴포넌트와 API는 T2에 있으나 공통 셸의 라우트 및 메인 링크 등록은 T1 작업이다.
- 통합 GUI E2E는 두 브랜치의 셸·Chat 변경을 합친 뒤 실행한다. 단위/빌드 성공은 GUI E2E를 의미하지 않는다.
